## Follow-ups (not done; for the maintainer to decide)

- A queued verify repair whose probe succeeds but whose repair then fails transiently (slow upstream, BUSY between probe and repair) pauses tailing for up to `REPAIR_TIMEOUT` per attempt and can repeat, keeping the replica out of ISR (final re-review m1).
- A stale `Force::Policy(Diverged)` request is not cleared by a later RESUME and outranks a later `MismatchPolicy::Rebootstrap` request for the rest of the generation (m2).
- The "probe succeeded" flag is not reset when the pending repair goes away (m4); a cancelled server bootstrap can release its permit before its blocking snapshot task finishes (m7); a probe's session close is only polled while the tail loop is idle (m8).
- Server verify/fetch computations are not cancelled when their session ends (only on shutdown/disconnect).
- Epoch history grows by one record per master open, without bound.
- Promotion gives no warning on a replica a verify found damaged.
- Throughput: group commit (one fsync per batch of queued writers) is the cheap win if write throughput becomes a limit; per-namespace logs / a replication mesh are better built as separate instances per shard (discussed, not scheduled).
